# Anti-slop audit 001

Date: 2026-10-08 (Asia/Manila). Mode: After, selected by the user. Rules: anti-slop 3.2.20, core plus mobile, accessibility, UI, and copywriting skills.

This report audits the existing application. No application code was changed. Findings are ordered by practical impact. All eleven findings fall under the skill's HIGH-priority Hard Gate rules; that classification is the rule tier, not an assertion that every issue has equal severity.

## Coverage and limits

- Ran the existing application at http://127.0.0.1:8000 in the in-app browser.
- Tested public home layout at widths 320, 375, 640, 768, 1024, and 1440 px. Inspected the stall browser, stall application form, sign-in dialog, application-status validation, and privacy page.
- Used the documented local demo accounts to inspect all fifteen admin pages at 375 px and all five tenant pages at 320 px. Checked admin dashboard and floor editor at tablet/desktop widths as well. Logged out after inspecting each account.
- Inspected the public light/dark theme switch. Most authenticated checks used dark mode. This is not a full certification of both themes.
- Tested keyboard focus and inspected rendered labels, dialog states, control geometry, computed styles, and console output. Calculated sampled contrast using the bundled contrast checker and alpha compositing of the rendered colors.
- Reviewed shared CSS, layout/navigation templates, authentication/profile forms, floor editor, ticket windows, and policy templates.
- Did not create applications, change leases, pay invoices, send messages, upload documents, or change settings. Did not open support conversations because they poll `markAsRead`; the chat geometry finding is source-based.
- Physical-device keyboards, browser zoom, every interactive control, network failures, OAuth, payment checkout, export files, and receipt PDFs were not exhaustively tested. No build or automated test suite was run because this audit changed no application code.

## Findings

### 1. HIGH: Shared header overflows on phones and tablets

**Rules:** R-03. **Reason:** Navigation and account actions extend beyond the visible viewport.

**Browser confirmed.** On the logged-out home page:

| Viewport width | Document scroll width | Outcome |
| --- | --- | --- |
| 320 | 462 | Overflow |
| 375 | 462 | Overflow |
| 640 | 701 | Overflow |
| 768 | 786 | Overflow |
| 1024 | 1009 | Contained |
| 1440 | 1425 | Contained |

Scrollbars account for the smaller document widths on desktop. At 375 px, Register extends to approximately x=462. Public stall and application-status pages inherit the same header problem. All five tenant pages measured a 326 px document width at a 320 px viewport; the account-control row extended to x=325.25.

**Source:** [navigation.blade.php](<C:/Users/John Lloyd Ramos/Desktop/Projects/Stall-Management-System-Center-Point/resources/views/layouts/navigation.blade.php:1>).

**Suggested fix:** Give the brand and controls an explicit narrow-screen layout, limit the brand's width, and move secondary public actions into an accessible mobile menu. Check the transition around 640 and 768 px as well as 320 and 375 px. Contain or reflow the header instead of hiding page overflow.

### 2. HIGH: Support chat has fixed dimensions that clip on small screens

**Rules:** R-03. **Reason:** A 320 px-wide, 520 px-tall window cannot fit smaller usable viewports with its fixed offsets.

**Source confirmed; not opened in the browser.** Both tenant and admin chat use `fixed bottom-4 right-4 w-80 md:w-96 h-[520px]`. At a 320 px-wide usable viewport, a 320 px window with a 16 px right offset begins at x=-16. With a vertical scrollbar the available width is smaller. At 480 px viewport height, the 520 px panel plus 16 px bottom offset starts above the screen. The window uses `overflow-hidden` and has no viewport-relative maximum height.

**Sources:** [tenant chat](<C:/Users/John Lloyd Ramos/Desktop/Projects/Stall-Management-System-Center-Point/resources/views/livewire/user/ticket-manager.blade.php:143>), [admin chat](<C:/Users/John Lloyd Ramos/Desktop/Projects/Stall-Management-System-Center-Point/resources/views/livewire/admin/ticket-center.blade.php:170>).

**Suggested fix:** Use a mobile full-screen or inset panel, responsive width, and a height bounded by the dynamic viewport. Keep the message composer reachable in landscape and while the on-screen keyboard is open. Verify on a device before claiming keyboard coverage.

### 3. HIGH: Sidebar and theme controls are not keyboard-operable

**Rules:** R-32. **Reason:** Visible label-based controls cannot be reached and activated as buttons.

**Browser and source confirmed.** The sidebar trigger and overlay are labels with `tabIndex=-1` and no keyboard handler. The theme label also has `tabIndex=-1`; its checkbox has `display:none`. The accessibility snapshot exposes the theme switch as a generic container, not a usable switch or button. Adding an accessible name to a label does not make it focusable.

**Sources:** [sidebar trigger](<C:/Users/John Lloyd Ramos/Desktop/Projects/Stall-Management-System-Center-Point/resources/views/layouts/navigation.blade.php:7>), [theme control](<C:/Users/John Lloyd Ramos/Desktop/Projects/Stall-Management-System-Center-Point/resources/views/layouts/navigation.blade.php:62>), [drawer overlay](<C:/Users/John Lloyd Ramos/Desktop/Projects/Stall-Management-System-Center-Point/resources/views/layouts/app.blade.php:97>).

**Suggested fix:** Use native buttons or a focusable checkbox/switch with an associated label. Give the sidebar trigger an accessible name, `aria-expanded`, and `aria-controls`; support Escape and restore focus on close.

### 4. HIGH: Shared focus-ring CSS uses the wrong color syntax

**Rules:** R-32, R-34. **Reason:** The focus outline disappears because DaisyUI's OKLCH token is inserted into `hsl()`.

**Browser confirmed.** The CSS declares `outline: 2px solid hsl(var(--p))`. In the current dark theme, `--p` is `65.69% .196 275.75`, an OKLCH triplet. After keyboard-tabbing to the dashboard's 6M button, `:focus-visible` was true while the computed outline style was `none`. The declaration overrides the useful component outline with an invalid computed color.

**Source:** [app.css](<C:/Users/John Lloyd Ramos/Desktop/Projects/Stall-Management-System-Center-Point/resources/css/app.css:112>).

**Suggested fix:** Use a valid `oklch(var(--p))` color or an explicit accessible focus token. Verify buttons, inputs, selects, and textareas by keyboard in both themes.

### 5. HIGH: Dialog visibility and focus management are broken

**Rules:** R-32, R-26. **Reason:** Open dialogs do not contain focus, and closed dialogs leave invisible controls in the tab order.

**Browser confirmed.** The sign-in dialog is rendered as `<dialog class="modal modal-open">` with `open=false`. Opening it leaves focus on the background Sign In button. Pressing Tab moves to the background Register button. The stall dialog similarly does not move focus into the dialog and has no accessible name.

The global modal CSS forces closed native dialogs to `display:flex !important`. Terms and privacy dialogs then remain rendered at opacity 0 with `visibility:visible`. Tabbing from the footer Terms & Conditions link enters the invisible terms dialog's Close button. Both hidden dialogs are present in the accessibility snapshot.

**Sources:** [modal CSS](<C:/Users/John Lloyd Ramos/Desktop/Projects/Stall-Management-System-Center-Point/resources/css/app.css:135>), [auth dialogs](<C:/Users/John Lloyd Ramos/Desktop/Projects/Stall-Management-System-Center-Point/resources/views/livewire/auth/auth-modals.blade.php:3>), [stall dialog](<C:/Users/John Lloyd Ramos/Desktop/Projects/Stall-Management-System-Center-Point/resources/views/livewire/portal/stall-browser.blade.php:88>).

**Suggested fix:** Centralize dialog behavior. Preserve native closed-dialog hiding, open native dialogs through their modal lifecycle, or implement focus trapping and background inertness for custom dialogs. Supply a name, move focus on opening, restore it on closing, and test nested policy dialogs with Escape.

### 6. HIGH: Form labels and validation errors lack programmatic associations

**Rules:** R-32, R-27. **Reason:** Assistive technology cannot consistently identify fields or connect validation messages to them.

**Browser confirmed for sign-in and application status; additional instances source confirmed.** Sign-in email and password inputs have no associated labels and no `aria-label`. Their visible labels are siblings without `for`/`id`. The same pattern appears in registration and profile forms.

Application-status fields have proper labels, but an empty lookup produces visible errors without `aria-invalid`, `aria-describedby`, or an announced error summary. Similar unassociated error spans appear in authentication forms.

**Sources:** [sign-in fields](<C:/Users/John Lloyd Ramos/Desktop/Projects/Stall-Management-System-Center-Point/resources/views/livewire/auth/auth-modals.blade.php:33>), [profile fields](<C:/Users/John Lloyd Ramos/Desktop/Projects/Stall-Management-System-Center-Point/resources/views/livewire/profile/profile-modal.blade.php:55>), [status fields](<C:/Users/John Lloyd Ramos/Desktop/Projects/Stall-Management-System-Center-Point/resources/views/livewire/portal/application-status.blade.php:8>).

**Suggested fix:** Associate visible labels with unique input IDs, connect error IDs to fields, expose invalid state, and announce validation feedback. Preserve the stall application's existing wrapping labels.

### 7. HIGH: Floor-map placement cells require a mouse

**Rules:** R-32, R-03. **Reason:** Selecting a stall by keyboard does not provide a keyboard-operable destination cell.

**Browser and source confirmed.** Placement cells are clickable divs with `tabIndex=-1`, no role, and no key handler. The unassigned stall picker offers buttons, but the second step, choosing a cell, cannot be completed by keyboard. Removal controls use `opacity-0 group-hover:opacity-100`, without a focus or touch-specific reveal.

**Source:** [stall-grid-editor.blade.php](<C:/Users/John Lloyd Ramos/Desktop/Projects/Stall-Management-System-Center-Point/resources/views/livewire/admin/stall-grid-editor.blade.php:67>).

**Suggested fix:** Provide keyboard-operable cell controls or a documented grid keyboard pattern. Retain drag-and-drop as an optional shortcut. Reveal removal actions on focus and touch, and avoid nesting a button inside another button when refactoring cells.

### 8. HIGH: Dark-theme stall and grid text fails the contrast requirement

**Rules:** R-25. **Reason:** Important small text becomes too faint after opacity is applied.

**Rendered colors sampled and calculated.** Contrast calculations converted the computed OKLCH colors to sRGB, composited their alpha over the card background, and used the skill's contrast checker. These are sampled failures, not an exhaustive palette audit.

| Text sample | Effective text RGB | Effective background RGB | Contrast |
| --- | --- | --- | --- |
| Public occupied stall label | 92, 99, 111 | 19, 24, 35 | 2.92:1 |
| Occupied floor-map coordinate | 74, 93, 113 | 14, 39, 63 | 2.24:1 |
| Empty floor-map coordinate | 77, 84, 99 | 17, 24, 41 | 2.32:1 |

The checker used unrounded channel values. These labels are normal small text, requiring 4.5:1 under R-25. The public occupied control remains actionable, so its information is not simply disabled content.

**Sources:** [occupied stall style](<C:/Users/John Lloyd Ramos/Desktop/Projects/Stall-Management-System-Center-Point/resources/views/livewire/portal/stall-browser.blade.php:5>), [grid coordinate style](<C:/Users/John Lloyd Ramos/Desktop/Projects/Stall-Management-System-Center-Point/resources/views/livewire/admin/stall-grid-editor.blade.php:80>).

**Suggested fix:** Use readable status and secondary-text tokens instead of dimming text opacity. Recalculate the actual composed colors in light and dark themes, including the smaller status text inside each stall cell.

### 9. HIGH: Frequent mobile controls miss anti-slop's 44 px target

**Rules:** R-03. **Reason:** Common actions retain compact desktop hit areas on phones.

**Browser confirmed.** At 375 px, Sign In, Register, the theme control, and floor tabs were 32 px tall; the theme control was 32 by 32 px. Stall application inputs and its file control were also 32 px tall. Close controls use the same compact button sizing. The skill explicitly requires a 44 px minimum; this is the anti-slop requirement, not a claim that every smaller control automatically violates every accessibility standard.

**Sources:** [navigation controls](<C:/Users/John Lloyd Ramos/Desktop/Projects/Stall-Management-System-Center-Point/resources/views/layouts/navigation.blade.php:40>), [floor tabs](<C:/Users/John Lloyd Ramos/Desktop/Projects/Stall-Management-System-Center-Point/resources/views/livewire/portal/stall-browser.blade.php:29>), [application inputs](<C:/Users/John Lloyd Ramos/Desktop/Projects/Stall-Management-System-Center-Point/resources/views/livewire/portal/stall-browser.blade.php:119>).

**Suggested fix:** Give mobile actions and form controls a minimum 44 px hit area and adequate spacing. Keep compact desktop sizing where useful. Coordinate this change with finding 1 so enlarged controls do not worsen header overflow.

### 10. HIGH: Floor tabs do not expose selected state or tab relationships

**Rules:** R-32. **Reason:** Visual selection is not conveyed through the tab semantics already declared by the component.

**Source and rendered DOM confirmed.** The floor selector uses `role="tablist"` and `role="tab"`, but has no `aria-selected`, controlled panel IDs, or roving tab index. Selection is communicated only through the `tab-active` class. No arrow-key handling exists in the template.

**Source:** [floor tabs](<C:/Users/John Lloyd Ramos/Desktop/Projects/Stall-Management-System-Center-Point/resources/views/livewire/portal/stall-browser.blade.php:29>).

**Suggested fix:** Implement a complete tabs pattern with selected state, tab/panel relationships, and keyboard navigation, or simplify the semantics to ordinary floor-selection buttons with an exposed pressed/selected state.

### 11. HIGH: Policy pages fabricate their update date on every request

**Rules:** R-38. **Reason:** The displayed revision date is the current rendering date rather than evidence of a policy revision.

**Source confirmed.** Privacy and terms templates both render `Last updated: {{ date('F d, Y') }}`. The date changes daily even if their stored policy content is unchanged.

**Sources:** [privacy date](<C:/Users/John Lloyd Ramos/Desktop/Projects/Stall-Management-System-Center-Point/resources/views/pages/privacy.blade.php:6>), [terms date](<C:/Users/John Lloyd Ramos/Desktop/Projects/Stall-Management-System-Center-Point/resources/views/pages/terms.blade.php:6>).

**Suggested fix:** Display a real revision timestamp stored when the corresponding policy changes, or omit the date until such a timestamp exists.

## What already holds up

- All fifteen admin pages loaded at 375 px without page-wide overflow in their default states. Wide tables, the 720 px calendar, and the floor editor were contained within horizontal scroll regions. Contained map/table scrolling is purposeful and is not classified as a page-overflow defect.
- The public floor map similarly contains its 568 px grid inside a roughly 286 px scroll area at 375 px. Its page overflow comes from the shared header.
- Dashboard cards and several forms already use responsive grid breakpoints.
- The stall application has associated wrapping labels, upload feedback, visible validation slots, and a submitting state.
- Application-status lookup shows useful validation messages and has properly associated visible labels.
- Public navigation uses real application destinations. Home-page stall and floor counts come from model queries rather than hardcoded marketing statistics.
- No warnings or errors were captured in the sampled home/sign-in and admin sign-in console checks. This does not certify all pages or interactions.

# Browser QA audit

Mode: after, selected for this session. Scope: the browser suite, its comments and documentation, and the application request-error feedback added to resolve finding 1.

## Findings

1. **HIGH. R-27: ticket submission had no clear, recoverable request error alert.** The initial run's injected HTTP 400, 401, 404, and 500 responses displayed Livewire's raw-response iframe instead of a visible application alert with a next action. A failed connection also lacked the requested alert. These five failures required application request-failure handling that explains the failure, preserves the draft, offers recovery, and directs an expired session to sign-in.

Finding 1 is **resolved**. The shared JavaScript entry point registers Livewire's request-failure hook once, suppresses the raw-response popup, and renders one persistent `role="alert"` inside the active form/dialog or above page content. It preserves drafts, restores pre-submission disabled/read-only states on failure, and never automatically repeats a write. Session errors offer sign-in in a separate tab and explain stale-page recovery before a reload.

The final Chromium run passed all 51 scenarios, including 11 error/recovery cases. The five original failures now pass with manual retry without reload. Actual session expiry, guest keyboard dismissal and login retry, cached navigation, narrow light/dark dialogs, and page-level recovery also pass. The application error-state gate for finding 1 is closed.

## Suite review

The comments explain three constraints: Chromium discarding an authentication response during navigation, native date inputs preventing malformed values, and a debug iframe being insufficient error feedback. They contain no decorative headings or step-by-step narration.

The run guide names the actual commands, fixtures, isolation paths, failure artifacts, and coverage limits. Fixture identities use the E2E label and `.test` addresses. Test messages and simulated errors are identified as QA data. The documentation makes no production throughput, payment-provider, or accessibility certification claim.

The request handler's comments explain the overlap between Livewire's form and loading directives. Additional test comments explain persistent-alert timing and cached dialog restoration. No additional comment or documentation findings require a rewrite.

The alert reuses the application's existing error palette and controls. Desktop page alerts occupy normal document flow so they do not obstruct the action that failed. Narrow dialog alerts stack text and recovery controls; screenshot review confirmed readable, unclipped light/dark states. The sign-in link opens the existing route in a separate tab, the dismiss button supports keyboard activation and restores focus, and successful manual retries clear the alert. The tests confirm a minimum 44-pixel sign-in target height. No new branding direction or decorative UI was introduced.

## Verification

Build and TypeScript checks, JavaScript syntax checking, and the full Chromium run passed. Previous PHP helper/router and Node support-script checks remain applicable; those files were unchanged by this fix. The final run totals and covered interactions are recorded in `docs/e2e-qa-results.md`. Explicit error-state screenshots are retained in the passing report; the harness retains traces, video, and diagnostic attachments when a test fails.

Cached-history CSP console errors observed during investigation remain outside this request-alert finding. Navigation and recovery pass, but this audit does not claim that all application console output is clean.

An early Windows harness run placed HTTP sessions/cache in normal application storage. PHP now starts with `variables_order=EGPCS`, the router rejects a mismatched storage/database environment, the CLI helper validates storage paths, and each test checks that HTTP sessions exist in the isolated runtime. The test-created registration throttle was backed up and removed. Database mutations remained confined to the dedicated SQLite database throughout.
